- Dodano typowane snapshoty konfiguracji entrypointów API i workera. API ładuje jeden nieruchomy snapshot przed tworzeniem Nest providerów, oddziela bezpieczne ustawienia od sekretów (w tym URL Redis z hasłem) i wymaga w produkcji odpowiednio długich sekretów sesji, limitu logowania i autoryzacji workera. Snapshot obejmuje klucze szyfrowania artefaktów i maili, proxy HTTP oraz katalogi eksportu i dziennika kasowania. Loader waliduje też adresy usług wewnętrznych i odrzuca URL z poświadczeniami, query lub fragmentem. Worker parsuje wymagane DB/profile/sekret, limity puli, flagi, kanał przeglądarki i receiver. Sekretów nie zwracają błędy ani komunikaty diagnostyczne. Inne procesy/CLI nadal pobierają własne typed config na początku działania; pozostałe bezpośrednie odczyty środowiska w adapterach i punktach startowych są jawnie przekazywane lub pozostają do przeglądu.
- Dodano typowane konfiguracje dla migratora, runtime grants, bootstrapu administratora, enrichment workera i import parsera. Każda konfiguracja DB podaje oczekiwaną rolę, a kontrola rzeczywistego `current_user` pozostaje przed pracą; enrichment dostaje allowlistę ustawień providerów, import parser waliduje sekret/host/port, a bootstrap może pominąć dane logowania, jeśli baza jest już zainicjalizowana. API, migrator i enrichment ustawiają jawny URL przed pierwszym użyciem lazy Sequelize.
- API trzyma ustawienia poczty (nadawcę, origin i dostawcę) w bezpiecznym snapshotcie, a Resend key osobno w snapshotcie sekretów; auth-mail dispatcher, recovery i provider nie czytają już środowiska ponownie po starcie API. Klient import parsera bierze URL/sekret z tych samych snapshotów. Przegląd entrypointów potwierdził, że bezpośrednie użycie `process.env` w pozostałych skryptach API/workera należy do loaderów albo jawnych test harnessów.
- Worker ładuje teraz Redis, readiness API, forwardera wyników, staging, selektory profili/portali i pacing do jednego snapshotu startowego. `run-worker` przekazuje jawne, ograniczone konfiguracje do usług; `LiveRunProcessor`, `WorkerResultForwarder`, `WorkerResultStagingStore` i helper readiness nie mają już domyślnego odczytu globalnego `process.env`. W kodzie produkcyjnym workera `process.env` pozostaje bezpośrednio tylko w loaderze konfiguracji entrypointu. CLI smoke przekazują środowisko jawnie.
