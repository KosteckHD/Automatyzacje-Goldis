# CYB-007 — spójność uprawnień roli auditor

Priorytet P1 do rozstrzygnięcia przed odbiorem. Potwierdzono odczyt syntetycznego leada przez auditor z grantem view_results, podczas gdy instrukcja administratora i centralna polityka ograniczają tę rolę do audytu. Nie potwierdzono samodzielnego nadania grantu ani przekroczenia tenanta. Cel: jedna jawna polityka obowiązuje na poziomie API, serwisów i interfejsu.

## Kontrakt do przyjęcia

Plan rekomenduje wariant A, zgodny z obecną instrukcją administratora. To założenie planistyczne, nie dokonana decyzja biznesowa.

| Wariant | Znaczenie auditor | Warunek wdrożenia |
|---|---|---|
| A — rekomendowany | Wyłącznie dziennik audytu; grant narzędzia nie otwiera danych operacyjnych | Ograniczyć centralnie i usunąć lokalne wyjątki |
| B — jawny wyjątek | Wybrane dane operacyjne mogą być dostępne z osobnym grantem | Dokładnie określić pola, operacje i narzędzia oraz zmienić instrukcję i centralny kontrakt |

Nie zamykać sprawy samym stwierdzeniem, że funkcja jawnie dopuszcza auditor. Nie blokować też przypadkowo reviewer, który ma inne obowiązki. Poniższe kroki implementacyjne dotyczą wariantu A; testy wariantu B muszą zostać przepisane według zatwierdzonej macierzy.

## Pliki

- `apps/api/src/features/authorization/tool-access.ts`: maksymalne capability wynikające z roli.
- `authorization-policy.ts` i testy polityki: jeden kontrakt zamiast rozbieżnych list.
- `features/leads/business-leads.service.ts`: roleCanRead i list/get/export.
- `features/admin/admin-users.service.ts` oraz repozytoria mutacji: zmiana roli i niezgodne granty.
- Katalog narzędzi/session snapshots i inne serwisy danych operacyjnych: stosowanie wspólnego wyniku polityki.
- `docs/INSTRUKCJA_ADMINA.md`: ostateczna macierz.
- Testy: `tool-access.spec.ts`, rzeczywiste HTTP leadów oraz nowy test DB zmiany roli.

## Kroki implementacji

1. [ ] Spisać macierz role×narzędzie×discover/execute/view/download. Dla auditor w wariancie A wszystkie capability operacyjne są false, audit:read pozostaje zgodne z tenantem. Obecny wspólny odczyt wyników OC dla operator/manager ma być zachowany.
2. [ ] Wydzielić jedną funkcję ograniczenia roli stosowaną przy obliczaniu ToolAccessSnapshot, zanim wynik trafi do canAccessTool i listToolAccess. Stan available/maintenance/disabled i grant nie mogą przekroczyć limitu roli. Nie implementować osobnych niespójnych ograniczeń w każdym kontrolerze.
3. [ ] Zastąpić lokalne dopuszczenie auditor w leadach centralną polityką. Sprawdzić list/get/export, snapshoty, dashboard, raporty i powiadomienia ujawniające dane leadów. Lista ekranów nie jest dowodem pokrycia; zapisać dla każdego odpowiedni endpoint i serwis.
4. [ ] Endpointy administracyjne nadawania grantów odrzucają kombinację niedozwoloną dla aktualnej roli. UI przedstawia zgodne opcje, ale odmowa jest egzekwowana w backendzie.
5. [ ] Zmiana roli w istniejącej transakcji: blokada członkostwa i właściwych grantów → zapis nowej roli → dezaktywacja tylko niezgodnych capability → cofnięcie sesji → audyt. Zachować ochronę ostatniego admina i istniejące potwierdzenie operacji uprzywilejowanej.
6. [ ] Uzgodnić kolejność blokad także z równoległym nadaniem grantu. Przestarzały odczyt roli przed grant write nie może odtworzyć niedozwolonych praw po zmianie roli. W razie sporu transakcje odczytują aktualne członkostwo pod tą samą blokadą.
7. [ ] Dodać kontrolowaną komendę korekty dawnych grantów z dry-run: liczba dotkniętych członkostw i capability, tenant, identyfikatory zasobów; bez danych klientów. Apply transakcyjny i idempotentny, ze zdarzeniem audytowym. Nie usuwać wszystkich grantów całego użytkownika, jeśli dotyczą innych tenantów lub dozwolonych praw.
8. [ ] Po zmianie sesje auditor nie mogą prezentować narzędzia jako dostępnego. Zmiana klienta nie zastępuje odmowy bezpośredniego HTTP. Stare linki/otwarte karty otrzymują kontrolowaną odmowę i czyszczą widok danych.

## Macierz testów

| Test | Aktor i operacja | Wariant A — oczekiwanie |
|---|---|---|
| C007-01 | Auditor bez grantu: list/get/export leadów | Odmowa bez danych |
| C007-02 | Auditor ze starym view_results | Odmowa mimo grantu |
| C007-03 | Auditor ze starym download_results | Brak wygenerowanego eksportu i pobrania |
| C007-04 | Operator z grantem → auditor → nowy login | Stara sesja nieważna; nowa nie ma danych operacyjnych |
| C007-05 | Odczyt starego URL i katalogu narzędzi | API odmawia; sesja/katalog zgodne z polityką |
| C007-06 | Operator/manager/reviewer z dozwolonym zakresem | Pozytywne ścieżki działają jak przed zmianą |
| C007-07 | Auditor czyta audyt swojego i obcego tenanta | Swój dozwolony, obcy odrzucony |
| C007-08 | Grant write równolegle ze zmianą roli | Brak końcowego niedozwolonego capability |
| C007-09 | Dry-run i dwukrotne apply korekty grantów | Dry-run bez efektów; drugie apply bez nowych zmian |
| C007-10 | Awaria audytu podczas zmiany roli/korekty | Pełny rollback roli/grantów/sesji danej transakcji |

C007-04/08/10 wymagają prawdziwego PostgreSQL i rzeczywistych metod mutacji. Dla HTTP nie stubować BusinessLeadService. Sprawdzić również odpowiedzi snapshot/report, nie tylko przycisk listy leadów.

## Odrębny temat — praca przyjęta przed revoke

Nie uznawać tej niespójności roli za dowód, że wszystkie wcześniej przyjęte zadania muszą zostać anulowane po revoke. Osobno zdefiniować: czy zatwierdzona praca jest operacją organizacji, czy zatrzymuje się na najbliższej bezpiecznej granicy. W drugim wariancie użyć unieważnienia dopuszczenia/fencingu, nie dostępu workera do pełnej tabeli użytkowników. Potrzebne testy: revoke przed claim, w trakcie lease i przed publikacją. To osobny kontrakt do zapisania, bez nowego numeru potwierdzonej luki.

## Wdrożenie i zamknięcie

Najpierw centralna odmowa, później korekta historycznych grantów, następnie weryfikacja katalogu i dokumentacji. Nie odtwarzać usuniętych praw automatycznie przy rollbacku aplikacji. Jeżeli wybrano B, przed wydaniem opublikować jednoznaczną macierz i testy zakresu pól.

Zamknięcie: zapisany wariant kontraktu, pełny zestaw C007 i zgodne API/UI/dokumentacja. Bez wyboru kontraktu status pozostaje `POLICY_DECISION_PENDING`, nawet jeżeli wszystkie testy obecnego zachowania są zielone.
