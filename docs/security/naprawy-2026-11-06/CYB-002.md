# CYB-002 — ochrona rewizji przed równoczesną edycją

Priorytet P1, waga wstępna średnia. Serwis przyjął dwa zapisy tej samej rewizji z adapterem pamięciowym; wyścig PostgreSQL pozostaje do potwierdzenia. Cel: z tej samej rewizji szkicu może powstać tylko jedna zaakceptowana następna rewizja.

## Pliki i decyzja implementacyjna

Zmienić `apps/api/src/features/commissions/commissions.service.ts` oraz testy repozytorium/serwisu. Użyć istniejących `CommissionsRepository.transaction`, `findOne(... transaction, lock)` i `save(... transaction)`. Preferowane rozwiązanie: blokada wiersza PostgreSQL w jednej transakcji, zgodna ze wzorcem istniejącego publishDictionary. Nie dodawać drugiego, równoległego mechanizmu wersjonowania Sequelize, jeśli nie jest potrzebny.

Proponowane nowe testy: `commissions.dictionary-concurrency.db-integration.spec.ts` oraz test kontraktu HTTP 409. Dodać je do faktycznego runnera DB/CI. Sam wzorzec nazwy nie wystarcza.

## Niezmienniki

- Snapshot, jego hash i revision są jedną zmianą.
- Status draft i expectedRevision są sprawdzane po uzyskaniu blokady, na świeżym rekordzie.
- Zmiana nie przechodzi na archived/published, nawet jeśli była draft podczas wcześniejszego odczytu.
- Filtr obejmuje tenantId i dictionaryVersionId.
- Sukces jest zwracany dopiero po zatwierdzeniu transakcji razem z audytem CYB-003.

## Kroki implementacji

1. [ ] Wykonać walidację CYB-001 i podstawową kontrolę uprawnień. Nie otwierać transakcji dla błędnego formatu żądania.
2. [ ] Otworzyć transaction; odczytać rekord po tenantId i dictionaryVersionId z `lock: transaction.LOCK.UPDATE`. Weryfikować status w transakcji. Dla znanego, nieedytowalnego rekordu można zwracać 409 `COMMISSION_DICTIONARY_NOT_EDITABLE`; dla obcego lub nieistniejącego 404. Ujednolicić zachowanie z publikacją i testami.
3. [ ] Po blokadzie porównać aktualną revision z expectedRevision. Przy różnicy rzucić istniejący konflikt `COMMISSION_DICTIONARY_REVISION_CONFLICT`; nie odszyfrowywać i nie zapisywać nowej wersji.
4. [ ] Odszyfrować lokalną kopię snapshotu, zastosować zmianę, wyliczyć hash i zaszyfrować. Podnieść revision dokładnie o jeden. Zapisać wszystkie pola z tą samą transaction.
5. [ ] Przekazać transaction do audit.record według CYB-003. Nie zwracać obiektu sukcesu poza kontraktem zarządzanej transakcji przed commit.
6. [ ] Przejrzeć edit/publish/activate pod kątem wspólnej kolejności blokad. Edycja blokuje pojedynczy szkic; operacje zmieniające aktywną wersję mogą blokować więcej rekordów i muszą używać deterministycznej kolejności. Nie dodawać blokady globalnej całego tenanta do zwykłej edycji bez potrzeby.
7. [ ] W formularzu po 409 odświeżyć szkic i pokazać konflikt. Nie ponawiać automatycznie zapisu na nowej rewizji, bo mogłoby to nadpisać cudzą zmianę. Zachować lokalne wartości użytkownika do świadomego ponowienia.

## Testy z prawdziwym PostgreSQL

| Test | Przebieg | Oczekiwanie |
|---|---|---|
| C002-01 | Dwa niezależne połączenia, ten sam szkic i expectedRevision, różne stawki | Dokładnie jeden sukces i jeden 409 |
| C002-02 | Po C002-01 odczyt z nowego połączenia | revision zwiększona o 1, hash zgodny ze snapshotem zwycięzcy |
| C002-03 | Dwie zmiany różnych komórek przy tej samej rewizji | Druga także otrzymuje konflikt; nie gubimy po cichu pierwszej |
| C002-04 | Poprawne ponowienie po ponownym odczycie rewizji | Kolejny sukces i revision+1 |
| C002-05 | Publish wygrywa blokadę przed edit | Brak zmiany opublikowanego snapshotu |
| C002-06 | Edit wygrywa przed publish ze starą rewizją | Edit sukces, publish 409 |
| C002-07 | Różne szkice lub różni tenanci | Brak wzajemnego blokowania niepowiązanych zasobów |
| C002-08 | Błąd szyfrowania lub zapisu | Brak nowej rewizji i brak audytu sukcesu |

Wyścig sterować barierami w testowych adapterach repozytorium: pierwsza transakcja utrzymuje blokadę, druga rzeczywiście próbuje wykonać SELECT/UPDATE, następnie pierwsza jest zwalniana. Limit czasu ma przerwać zawieszony test, nie ustalać zwycięzcy. Końcowy odczyt wykonać po commit poza obiema transakcjami.

## Migracje i wdrożenie

Obecny schemat ma revision>0 oraz identyfikatory/indeksy tenanta; dla samej blokady nie jest wymagana migracja. Nie zmieniać historycznej migracji 066. Sprawdzić czas oczekiwania na blokadę i obsłużyć deadlock/lock timeout kontrolowanym błędem, bez ślepego automatycznego powtarzania edycji.

Wdrażać razem z CYB-003. W razie regresji wyłączyć mutacje szkicu; cofnięcie do nieatomowej edycji przy aktywnej współpracy odtwarza ryzyko. Zamknięcie wymaga wyników C002-01–08 na izolowanej bazie oraz testu formularza konfliktu. Test Promise.all z pamięciowym repozytorium pozostaje wyłącznie kontrolą lokalną.
