# CYB-006 — atomowa publikacja wyniku i anulowanie

Priorytet P1, waga wstępna średnia. Przy syntetycznym wyścigu snapshot i audyt sukcesu zapisano mimo zera rekordów zmienionych w warunkowym UPDATE runu. Nie wykazano pobrania takiego wyniku przez użytkownika. Cel: publikacja i anulowanie mają jednoznaczną kolejność, a przegrana operacja nie pozostawia częściowych efektów.

## Pliki i współdzielony mechanizm

Zmienić `apps/api/src/commission-worker.ts`, `features/commissions/commissions.service.ts` — cancelRun oraz repozytorium wykonania z CYB-005. Wspólna kolejność blokad wszystkich ścieżek: run→dispatch. Nowe testy: `commission-publication.db-integration.spec.ts`, kontrakt HTTP cancel i testy retry/failure.

Istniejący unique snapshotu po run_id zapobiega dwóm wierszom, ale nie nadpisaniu treści przez ON CONFLICT DO UPDATE. Nie jest to wystarczająca idempotencja.

## Niezmienniki

- Snapshot wyniku, result_sha256, counters, stan runu, stan dispatchu i audyt sukcesu są zatwierdzane razem.
- Tylko aktualny token ważnej próby w stanie running może rozpocząć publikację.
- Zatwierdzone cancel_requested/cancelled wyklucza późniejszą publikację tej próby.
- Zatwierdzony wynik terminalny nie jest nadpisywany przez cancel, retry ani spóźniony markFailure.
- Anulowanie jest idempotentne; powtórzenie nie dopisuje kolejnego zdarzenia tej samej zmiany.

## Publikacja — kolejność w jednej transakcji

1. [ ] Walidację kontraktu odpowiedzi silnika i przygotowanie ciphertext/hash wykonać przed transakcją, żeby skrócić czas blokady. Te obliczenia nie dają prawa publikacji.
2. [ ] Rozpocząć transaction; zablokować run po tenantId/runId, potem powiązany dispatch. Ponownie sprawdzić status running, active_attempt_token, ważność lease z CYB-005 i dopuszczony stan dispatchu.
3. [ ] Gdy token/stany są nieaktualne, zakończyć jako obsolete bez zapisu wyniku i sukcesu. Dla cancel_requested przejść do kontrolowanej finalizacji cancel, a nie wyjątku, który zewnętrzny handler zamieni na failed.
4. [ ] Dla aktualnej próby wykonać warunkowy UPDATE runu z RETURNING lub kontrolą jednego zmienionego rekordu. Warunek nadal obejmuje tenant/run/token/status. Zero rekordów przerywa całą transakcję.
5. [ ] Zapisać snapshot bez bezwarunkowego nadpisania istniejącego wyniku terminalnego. W przypadku istniejącego snapshotu w running wykryć rozbieżność i zakończyć kontrolowanym błędem integralności; nie ukrywać jej automatycznym nadpisaniem.
6. [ ] Oznaczyć dispatch completed z kontrolą jednego wiersza i dopisać jeden audyt sukcesu. Dopiero commit czyni wszystkie efekty widocznymi. Awaria dowolnego etapu wycofuje także wcześniejszy UPDATE runu.
7. [ ] Duplikat po commit jest rozpoznawany przez terminalny run, więc nie dochodzi ponownie do audytu. Jeśli potrzebny jest dodatkowy klucz idempotencji audytu, dodać go w odrębnym, uzasadnionym schemacie, nie przez kasowanie zdarzeń append-only.

## Anulowanie — kolejność

1. [ ] cancelRun otwiera transakcję i używa tych samych blokad. Dla braku/obcego tenanta zwraca 404 bez ujawniania zasobu.
2. [ ] Dla queued ustawia cancelled, finishedAt oraz dispatch cancelled i zapisuje audyt w jednej transakcji. Późniejszy delivery jest no-op.
3. [ ] Dla running ustawia cancel_requested i odpowiedni etap oraz audyt. Po commit można best-effort wysłać cancel do silnika dla zapamiętanego tokenu; sieci nie trzymać wewnątrz blokady DB. Brak odpowiedzi silnika nie odwraca zatwierdzonego żądania anulowania.
4. [ ] Dla cancel_requested powtórne żądanie zwraca bieżący status bez kolejnego zapisu. Finalizacja cancelled należy do aktualnego workera/recovery, który potwierdzi stan pod blokadą.
5. [ ] Dla completed/completed_with_findings/failed/cancelled zwraca stan terminalny bez zmiany. Zachować obecne zachowanie zwracania statusu, o ile kontrakt HTTP nie wymaga jawnie konfliktu.
6. [ ] Zewnętrzne catch/finally i markFailure nie mogą później zmienić anulowanego runu na failed lub queued. Każda mutacja sprawdza stan i token; utrata własności próby oznacza brak efektów.

## Wyniki dwóch kolejności wyścigu

| Pierwszy commit | Druga operacja | Wynik |
|---|---|---|
| cancel_requested | Worker próbuje publikacji | Brak snapshotu i sukcesu tej próby; kontrolowana finalizacja anulowania |
| completed | API próbuje anulowania | Odpowiedź z completed; wynik i audyt sukcesu pozostają bez zmian |
| queued→cancelled | Konsument próbuje claim | Brak uruchomienia silnika |
| Recovery z nowym tokenem | Stara próba kończy obliczenie | Stary wynik odrzucony bez mutacji |

Granica gwarancji dotyczy commitów bazy, nie momentu kliknięcia przycisku przez użytkownika. UI nie może obiecywać anulowania, zanim odpowiedź API potwierdzi właściwy stan.

## Wdrożenie i stan historyczny

Dodatkowa migracja nie jest konieczna dla samej transakcji; pola lease wprowadza CYB-005. Przed wznowieniem workera wykonać tylko odczytowy raport rozbieżności, np. snapshot przy cancel_requested lub dispatch completed przy nieterminalnym runie. Nie usuwać snapshotów automatycznie i nie przepisywać historii audytu; sposób rekonsyliacji zatwierdzić według stanu i pochodzenia danych.

Wdrożenie/rollback wspólne z CYB-005. Zamknięcie wymaga C006-01–10 na rzeczywistym DB i zgodnego kontraktu UI. Brak zmiany liczby wierszy z UPDATE zawsze ma jawnie obsługiwaną ścieżkę, nie może być ignorowany.
