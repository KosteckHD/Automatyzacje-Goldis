# DEP-001 — uuid w zależnościach i spójność skanowanego środowiska

Priorytet P2 dla zgłoszenia uuid. To advisory zależności, nie wykazany exploit Goldis. Według audytu 3 wpisy moderate npm reprezentują uuid i ścieżki przez ExcelJS/Sequelize. Przejrzane wywołania rodziców używały v1/v4; podatny kontrakt dotyczył v3/v5/v6 z zewnętrznym buforem. Stan wersji i advisory trzeba ponownie sprawdzić podczas implementacji.

## Pliki

`package.json`, `package-lock.json`, manifesty workspace używających ExcelJS/Sequelize, `.github/workflows/backend-checks.yml`, `docs/security/DEPENDENCY_DECISIONS_2026_10_08.md` lub nowy aktualny rejestr decyzji. Dodatkowo `services/commission-engine/pyproject.toml`, `requirements.lock` i `Dockerfile` dla zgodności środowiska Python. Zmiany Python są powiązanym utrzymaniem, a nie dowodem drugiej luki uuid.

## Etap 1 — odtworzyć stan i osiągalność

1. [ ] Na czystej instalacji z aktualnego locka zebrać wersje i drzewo `npm ls uuid exceljs sequelize`. Zachować wynik produkcyjnego npm audit wraz z datą i hashem lockfile. Nie porównywać skanu starego node_modules z nowym lockiem.
2. [ ] Przeczytać aktualne advisory u źródła i potwierdzić podatne zakresy oraz faktycznie poprawione wersje. Używać aktualnego źródła, nie numeru zapamiętanego z raportu.
3. [ ] Przejrzeć importy i wywołania podatnych funkcji w aplikacji i rodzicach. Sprawdzić przekazywanie bufora/offsetu i źródło ich wartości. Zapis „nie znaleziono” oznacza granicę wykonanego przeglądu, a nie dowód niemożliwości wywołania.

## Etap 2 — wybór poprawki

1. [ ] Preferować zgodną, utrzymywaną aktualizację pakietów nadrzędnych, która rozwiązuje ich wymagania uuid. Aktualizować manifest i lock razem.
2. [ ] Nie stosować `npm audit fix --force`, proponowanych downgrade rodziców ani globalnego major override bez testu zgodności. Nowy uuid może zmieniać API lub sposób ładowania modułów; bezpośrednia zgodność własnego kodu nie gwarantuje zgodności rodzica.
3. [ ] Jeżeli nie ma zgodnej wersji rodzica, rozważyć mały, odtwarzalny patch konkretnej zagnieżdżonej zależności tylko z testami i właścicielem utrzymania. Nie edytować ręcznie node_modules jako trwałej poprawki. Fork/patch jest kosztem utrzymania do jawnego zaakceptowania.
4. [ ] Jeżeli podatna ścieżka pozostaje niewykazana i brak bezpiecznej aktualizacji, przygotować wyjątek: advisory, wersja/ścieżka, dowód użycia v1/v4, granica analizy, właściciel, termin maksymalnie 30 dni lub przed kolejnym wydaniem oraz warunek natychmiastowego przeglądu po zmianie użycia. To propozycja obsługi ryzyka; akceptacji dokonuje właściciel, nie agent.

## Etap 3 — zgodność Python i obrazu

1. [ ] Uzgodnić deklarację FastAPI w pyproject.toml z requirements.lock. Aktualny audyt wskazywał odpowiednio 0.116.1 i 0.162.0. Nie aktualizować wersji w ciemno: wybrać przetestowany zestaw i jedną metodę generowania locka.
2. [ ] Udokumentować instalację aplikacji i obrazu. Testy muszą wykonywać kod z tych samych zależności, które trafią do obrazu; obecny Dockerfile instaluje lock.
3. [ ] Zbudować czysty obraz, zebrać rzeczywiście zainstalowane pakiety, wykonać pip-audit/OSV i skan obrazu systemowego. Brak advisory dla 17 wpisów locka nie opisuje wszystkich bibliotek systemowych ani innej instalacji z pyproject.

## CI, wdrożenie i zamknięcie

W CI zachować wyniki skanów i hash locków jako artefakt, jawnie odróżniając błąd pobrania advisory od wyniku zero podatności. Wyjątek musi być wąski: konkretny advisory/ścieżka i termin, bez wyłączenia całego npm audit.

Rollback aktualizacji to spójny powrót manifestów, lockfile i obrazu, z zachowaniem informacji o otwartym advisory. Brak migracji danych wynikający z samej aktualizacji uuid; ewentualne migracje rodziców muszą mieć osobny przegląd.

Zamknięcie jako `REMEDIATED` wymaga usunięcia podatnej wersji i D001. Pozostawienie wersji z uzasadnieniem ma status `RISK_ACCEPTED` dopiero po decyzji właściciela; nie oznacza usunięcia podatności pakietu. Termin wyjątku jest częścią dokumentu decyzji, a nie nową automatyzacją utworzoną bez zlecenia użytkownika.
