# CYB-003 — zmiana słownika i audyt w jednej transakcji

Priorytet P1, waga wstępna średnia. Odtworzono save przed błędem adaptera audytu. Nie wykazano możliwości wymuszenia awarii przez zwykłego użytkownika. Cel: nie istnieje zatwierdzona edycja słownika bez odpowiadającego jej zatwierdzonego audytu sukcesu.

## Pliki i istniejące możliwości

`apps/api/src/features/commissions/commissions.service.ts`, `commissions.repository.ts`, `apps/api/src/features/audit/audit.service.ts`, `audit.repository.ts` — ostatnie dwa sprawdzić, nie zmieniać bez potrzeby. AuditService.record już przyjmuje opcjonalną transaction. Użyć istniejącego mechanizmu zamiast nowego, niezależnego połączenia lub kolejki do krytycznego audytu edycji.

Nowe testy: `commissions.dictionary-atomicity.db-integration.spec.ts`; dodatkowe testy adaptera potwierdzające przekazanie tej samej instancji transakcji.

## Kroki implementacji

1. [ ] Uzupełnić transakcję CYB-002: odczyt z blokadą → zmiana → save → audit.record(event, transaction) → commit.
2. [ ] Zweryfikować, że AuditRepository korzysta z tej transaction w faktycznym zapisie SQL, a nie jedynie przyjmuje argument. Wyjątek z zapisu audytu musi propagować się do zarządzanej transakcji.
3. [ ] Nie łapać błędu audytu i nie kontynuować sukcesem. Jeśli potrzebny jest osobny wpis o awarii, zapisać go po rollback w odrębnym, bezpiecznym kanale operacyjnym; nie nazywać go sukcesem edycji.
4. [ ] Powiązać zdarzenie z tenantem, aktorem, słownikiem i nową rewizją. Metadane ograniczyć do bezpiecznych identyfikatorów i statusu, zgodnie z assertAuditMetadataSafe. Nie dodawać całego snapshotu, sekretów ani danych klienta do logu błędu.
5. [ ] Utrzymać append-only uprawnienia audytu. Naprawa nie może wymagać UPDATE/DELETE audit_events przez rolę API.
6. [ ] Opisać niejednoznaczność utraty połączenia po COMMIT: odpowiedź błędna nie dowodzi rollbacku. Klient odczytuje bieżącą rewizję; ponowienie ze starą rewizją ma konflikt i nie tworzy ponownie zmiany. Nie obiecywać exactly-once odpowiedzi sieciowej.

## Przegląd podobnych operacji

To lista prac kontrolnych, a nie dodatkowe potwierdzone znaleziska:

| Metoda | Co sprawdzić i jak docelowo rozwiązać |
|---|---|
| importDictionary | Rekord pliku, szkic i audyt w jednej transakcji publikacji; przygotowany plik poza DB ma staging/kompensację i sprzątanie osieroconych plików |
| deleteFile | Atomowe oznaczenie deleted + audyt, fizyczne usunięcie przez idempotentny etap po commit |
| cancelRun | Zmiana stanu + audyt razem według CYB-006 |
| addResolution | Utworzenie rozstrzygnięcia + audyt w jednej transaction |
| createExport | Wygenerować plik poza transakcją; publikacja ready + audyt razem; kontrolowane sprzątanie pliku po błędzie publikacji |
| downloadExport | Audyt przed wydaniem danych, jak obecnie; nie deklarować cofnięcia bajtów już wysłanych klientowi |

Dla plików filesystem i PostgreSQL nie mają wspólnego rollbacku. Najpierw zaprojektować stan pending/ready/deleted i retry sprzątania; nie obejmować długiego wywołania silnika otwartą transakcją SQL.

## Testy i warunki odbioru

| Test | Wstrzyknięcie/operacja | Oczekiwany stan po zakończeniu |
|---|---|---|
| C003-01 | Sukces edycji | Nowa rewizja i dokładnie jeden odpowiadający audyt |
| C003-02 | Prawdziwy błąd INSERT audit_events po save | Rewizja, ciphertext i hash identyczne z początkowymi |
| C003-03 | Błąd save przed audytem | Brak edycji i audytu sukcesu |
| C003-04 | Wyjątek między audit INSERT a commit | Brak obu zapisów po rollback |
| C003-05 | Dwie edycje tej samej rewizji | Jeden audyt sukcesu, zgodny ze zwycięzcą CYB-002 |

C003-02 uruchamiać na dedykowanej bazie z testowym mechanizmem błędu INSERT, np. tymczasowym triggerem ograniczonym do syntetycznego zasobu. Uprawnienia testowego właściciela DB nie mogą trafić do konfiguracji aplikacji. Usuwać mechanizm w finally; sprawdzać stan z nowego połączenia. Sam wyjątek z mocka audit.record nie wystarcza do testu trwałości DB.

## Wdrożenie i wycofanie

Dla podstawowego zakresu brak migracji i brak czyszczenia danych historycznych. Wdrożyć razem z CYB-002. Przeprowadzić kontrolę historycznych rewizji i zdarzeń w osobnym, tylko odczytowym zadaniu, jeżeli właściciel danych potrzebuje oceny dawnych zmian; nie dopisywać fikcyjnych zdarzeń sukcesu wstecz.

Zamknięcie: wyniki C003-01–07 i brak niezależnego zapisu audytu w ścieżce edycji. Rozszerzenia na pliki/eksporty rozliczać osobno. W razie regresji wyłączyć edycję do poprawy; nie akceptować cichego pomijania audytu jako obejścia problemu.
