# CYB-005 — bezpieczne ponowne dostarczenie zadania prowizji

Priorytet P1, waga wstępna średnia. Rzeczywisty kod workera uruchomił zakończone zadanie przy syntetycznym ponownym dostarczeniu. Nie wykazano anonimowego wstrzykiwania zadań do Redis. Cel: ponowne dostarczenie nie uruchamia zakończonego zadania, a po awarii tylko jedna aktualna próba może publikować wynik.

## Pliki i podział odpowiedzialności

| Plik | Odpowiedzialność |
|---|---|
| `apps/api/src/commission-worker.ts` | Połączenie BullMQ i wywołania jawnych operacji claim/heartbeat/complete/fail |
| `apps/api/src/features/commissions/commission-execution.repository.ts` — nowy | Transakcje, blokady, aktualny token i lease |
| `apps/api/src/features/commissions/commission-execution-policy.ts` — nowy | Dozwolone przejścia i wynik obsługi duplikatu |
| `commissions.model.ts` | Dodatkowe pola lease, jeśli przyjęty projekt ich wymaga |
| Nowa migracja po obecnej 066 | Addytywne pola/indeksy lease; bez edycji historii migracji |
| Testy nowe `commission-execution.spec.ts`, `commission-execution.db-integration.spec.ts` | Model stanów i współbieżny odbiór DB/Redis |

Nie tworzyć importów z prywatnych wnętrz innych feature. Nową granicę serwisu/repozytorium wyeksportować przez publiczny moduł prowizji, jeśli wymaga tego architektura.

## Docelowy kontrakt

| Stan runu | Odbiór zadania |
|---|---|
| queued, dopuszczony dispatch | Jedna transakcja przejmuje pracę i ustawia nowy token próby |
| running z ważnym lease | Duplikat nie uruchamia silnika |
| running z wygasłym lease | Wyłącznie kontrolowane recovery może przejąć zadanie z nowym tokenem |
| completed / completed_with_findings / failed / cancelled | Brak wywołania silnika i brak zmiany danych terminalnych |
| cancel_requested | Kontrolowana finalizacja anulowania, bez publikacji wyniku |

Celowo zlecona nowa analiza jest nowym runem/idempotency key, a nie replay starego dispatchu. `commission_dispatches.attempt_count` liczy obecnie próby publikowania outboxu; nie używać go jednocześnie jako licznika prób wykonania bez zmiany kontraktu.

## Kroki implementacji

1. [ ] Wydzielić processJob od startu procesu i efektów importu modułu. Umożliwić testowanie rzeczywistych funkcji przez jawne zależności; nie polegać docelowo na dopisywaniu eksportu przez VM jak historyczny harness.
2. [ ] Rozdzielić odczyt diagnostyczny od przejęcia. readRunInput nie może sam dawać prawa wykonania ani dopuszczać completed do ścieżki uruchomienia. Claim zwraca jawny wynik `claimed`, `duplicate`, `terminal`, `cancelled` lub `obsolete`.
3. [ ] Claim wykonuje jedną transakcję: blokada runu i dispatchu w stałej kolejności run→dispatch; sprawdzenie relacji tenant/run/dispatch, dozwolonych stanów i tokenu; ustawienie running, nowego tokenu, lease i identyfikatora wykonawcy. Tylko po commit zwycięzca czyta pliki i wywołuje silnik.
4. [ ] Uzgodnić protokół także z claimDispatches/publishOutbox. Nie pozostawiać ścieżki, która trzyma blokadę dispatch i czeka na run, gdy claim/complete używa odwrotnej kolejności. Wybór kandydatów może być bez blokady, ale właściwe przejęcie zawsze ponownie sprawdza warunki.
5. [ ] Przetestować okno między queue.add i oznaczeniem dispatch jako published. Obecność stałego jobId i removeOnComplete=false nie może powodować trwałego zgubienia pracy, jeśli konsument zobaczy jeszcze publishing. Wybrać jawną politykę: akceptacja publishing przy poprawnym atomowym claim albo kontrolowane ponowienie bez sukcesu pustego joba. Nie kwalifikowano tego okna jako osobnej potwierdzonej luki; jest warunkiem odbioru zmiany.
6. [ ] Dla recovery dodać lease w bazie, np. execution_owner i execution_lease_until na runie oraz ewentualny licznik prób wykonania. Użyć już istniejącego active_attempt_token jako fencing tokenu; generować nowy przy każdym przejęciu. Nie używać claimed_by dispatchu jako potwierdzenia żywotności wykonawcy, bo jest własnością publishera.
7. [ ] Proponowane startowe parametry do testów: lease 90 sekund, heartbeat co 20 sekund, zegar PostgreSQL. Parametry są decyzją implementacyjną do sprawdzenia przy opóźnieniach DB; nie stanowią wyniku pomiaru. Heartbeat zmienia lease tylko przy zgodnym tokenie i dozwolonym stanie.
8. [ ] Po utracie heartbeat/lease worker nie publikuje. Może wysłać cancel tylko dla swojego tokenu i zakończyć próbę. Recovery przejmuje wyłącznie wygasły lease; stary proces zostaje nieskuteczny przez fencing także wtedy, gdy wróci po długiej pauzie.
9. [ ] markFailure i retry muszą sprawdzać token, stan i liczbę zmienionych rekordów. Przejście running→queued dla retry jest jawne, transakcyjne i nie obejmuje runu terminalnego/cancel_requested. Utrata prawa próby nie jest błędem, który wolno zapisać jako failed nowszego wykonania.
10. [ ] Publikację wyniku realizować przez wspólną operację CYB-006. Nie polegać na gwarancji pojedynczego dostarczenia z BullMQ; dostarczanie może być powtórzone, efekty DB muszą być idempotentne.

## Migracja i recovery

1. [ ] Dodać pola lease jako nullable oraz indeks potrzebny do skanowania running z wygasłym lease. Potwierdzić zapytaniem EXPLAIN na syntetycznym wolumenie; nie dodawać indeksów bez zapytania, które ich używa.
2. [ ] Zaktualizować prawa roli commission-worker tylko o wymagane kolumny/tabele. Nie przyznawać dostępu do sesji lub członkostw dla wygody.
3. [ ] Przed uruchomieniem nowych konsumentów zatrzymać starych. Istniejące running bez lease potraktować jako osobną kategorię do kontrolowanego recovery po potwierdzeniu braku starych procesów; nie uznawać ich w ciemno za wygasłe w mieszanym wdrożeniu.
4. [ ] Nie resetować terminalnych rekordów do queued. Raport rozbieżności dispatch/run obejmuje tylko identyfikatory, stany i liczniki; bez odszyfrowanych plików.

## Wdrożenie, rollback i zamknięcie

Wdrażać razem z CYB-006: zatrzymanie konsumentów → kompatybilna migracja → API i worker z jednym protokołem → kontrola stanów → syntetyczny replay → wznowienie. Nie uruchamiać starego i nowego workera jednocześnie.

Rollback najpierw zatrzymuje nowe procesy; schemat addytywny można pozostawić. Nie cofać fencing tokenów ani automatycznie reaktywować ukończonych runów. Jeżeli stara wersja nie respektuje lease, bezpiecznym wyjściem jest czasowe wstrzymanie prowizji do poprawy. Zamknięcie: C005-01–10 i zgodna kontrola CYB-006.
